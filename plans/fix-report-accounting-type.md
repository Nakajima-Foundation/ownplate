# 売上表の `accounting` を、戻り値の型で「必ずある」にする

## いまの形

`order2ReportData` は `accounting` が無ければその場で組み立ててから注文を返す。
つまり **戻ってきた注文は `accounting` を必ず持つ**。しかし戻り値の型は引数の型の
ままで、`ReportPage.vue` はそれを `ref<OrderInfoData[]>` で受けるので、テンプレートが
`order.accounting.food.revenue` と素直に読んでいる箇所が「無いかもしれない」と言われる。

## 変えたこと

**関数の本体は一行も変えていない。** 足したのは3つだけ。

- `ReportRow` — `accounting` が必須の型。export して `ReportPage.vue` が受ける
- `hasAccounting` — 型ガード。`as` を使わずに戻り値の型を絞るため
- 戻り値の型注釈と、ガードを満たさなかったときの例外

読む側に `?.` を足すのではなく、大元の宣言から省略可を外す形にした。

## `service` まで必須にするのは見送った

テンプレートには `order.accounting.service.revenue` を読む箇所もある。`service` も
必須にすれば通るが、**そのためには本体を書き換える必要があり、書き換えると振る舞いが
変わる**。測って確かめた結果は下記。

| 試した形 | 差 |
|---|---|
| `Object.assign(accounting, { service })` で型に伝える | 真値のスカラーで**差が出る**（旧は例外、新は箱に入れて売上ゼロの行を返す） |
| 素の代入に戻して `Object.assign(order, { accounting })` | `order.accounting` に setter があると**差が出る** |
| **本体そのまま + 型ガード（採用）** | **差ゼロ** |

売上の数字なので、うるさく落ちる旧の動作を、黙って food と alcohol の無い行に
変える方向の差は取らない。`service` の2件は残す。

## 同じ振る舞いであることの確かめ方

**読んで判断していない。** 旧実装をそのまま写して、新と並べて走らせた。

### 形を数え上げるのをやめ、規則を測った

区分の形を足しては測る、を三度やって三度足りなかったので、途中で向きを変えた。
言語には必ずもう一つ形があるので、禁じる形を並べる限り終わらない。

**この変更の実行上の差は一つだけ**のはず — 最後の書き込みのあとに
`order.accounting` を **1回多く読む**。書き込みは増やさない。これを直接測った。

読み書きを数える `order` を作り、区分の形・金額・税率・注文種別・地域・`multiple` を
総当たり（23,040通り）して、旧と新の読み回数・書き回数を突き合わせた。
**規則の破れはゼロ。** 旧が例外で終わる場合は守りに届かないので読みも増えない、
というところまで込みで成り立つ。

規則が予言するとおり、3回目の読みで例外を投げる getter では旧が返して新が落ちる。

### 形のほうも総当たりした

網羅した `accounting`: 未定義・null・偽値スカラー・真値スカラー・真偽値・空配列・
非空配列・空・凍結・封印・prototype 経由・`service` が既にある・`service` が getter だけ・
`service` の setter が値を捨てる・Proxy・`Number`/`String` の箱。これを、`order` 側が
素の場合・`accounting` に setter がある場合・`accounting` が読むたびに変わる場合の
3通りと掛け合わせ、さらに金額（0・負・小数・NaN・Infinity）、税率（0・負・-1・NaN）、
日時欄の有無、注文種別、地域、`multiple` を総当たり。

突き合わせたのは **戻り値・引数がどう書き換わったか・戻り値が引数と同一実体か・
`accounting` が同一実体か・setter が何回呼ばれたか・Proxy が何を受けたか・
例外の種類と文面**。

| 試した形 | 差 / 1,555,200 |
|---|---|
| `Object.assign(accounting, { service })` で型に伝える | 870,912 |
| 素の代入に戻して `Object.assign(order, { accounting })` | 622,080 |
| 本体そのまま + 守りが `service` まで見る | 414,720 |
| **本体そのまま + 守りは有無だけ（採用）** | **373,248** |

**差ゼロではない。** 採用した形の差はすべて「`order.accounting` が読むたびに変わる」
一形で、内訳は「旧は返す／新は落ちる」。これは上の規則が予言するとおりで、
素のオブジェクトでは余分な1回の読みは観測できない。Firestore の `doc.data()` は
素のオブジェクトを返すので、この差は実データでは作れない。

harness は壊して効きを確かめてある。守りを常に偽にする／埋める条件を反転／
食品の売上をずらす／サービス税をずらす／`type` を入れない／国外のサービス税をずらす、
の6通りで赤くなる。

## 残した試験

harness は捨てるが、これを見つけた**性質**は `test/unit/test_reportData.ts` に残した。

- 渡された区分の実体をそのまま返すこと
- すでに区分がある注文に `accounting` を書き戻さないこと
- 区分がオブジェクトでなかったら、`service` の代入で落ちること
- 区分が渡す直前に消えていたら、守りが落とすこと

見送った2つの形に差し替えると順に2件・1件が赤くなる。**守りだけを外すと、
消える区分の1件だけが赤くなる。** 戻すと全部緑に戻る。

守りは export していない。試験のためだけに公開面を広げないため、
`order2ReportData` 越しに検めている。

## 確かめていないこと

売上表の画面を開いていない。`accounting: {}` のような中身の欠けた区分は
この変更の前後で振る舞いが同じ（差ゼロ）だが、テンプレートが `food` を読む前提は
`OrderInfoData` の宣言そのものに元からあり、ここでは触っていない。`AllOrders.vue` も `order2ReportData` を呼ぶが、
そちらは `accounting` を読まないので受け取る型は変えていない。
