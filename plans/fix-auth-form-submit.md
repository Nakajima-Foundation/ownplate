# 認証画面の form ボタンが二重送信・誤送信する

omochikaeri-docs#163

## 何が起きていたか（実機で再現）

form の中のボタンは `type` を書かないと submit として振る舞う。`t-button`（`button.vue`）も
素の `<button>` も `type` を持たないので、form に置くとクリックで form が送信される。

dev サーバを立て、Firebase Auth へ実際に出たリクエストの数を Playwright で数えた:

| 操作（修正前） | 結果 |
|---|---|
| サインイン「次へ」を1回押す | 認証リクエストが**2回** |
| サインイン「キャンセル」 | **サインインが走る** |
| サインインでパスワード欄から Enter | **トップへ飛ばされる**（Enter は form 内の最初の submit ボタン＝キャンセルを押したことになる） |
| 新規登録「キャンセル」 | **アカウント作成が走る** |
| パスワード再設定「キャンセル」 | **再設定メールが送られる** |

issue が挙げていたのは1行目だけで、残りはこの調査で見つかった。

## `button.vue` に `type="button"` を足す（根本原因）

最初は足さなかった。PhoneLogin の送信ボタン2つが `@click` を持たず、`t-button` が form 内で
既定で submit になることに**依存して動いていた**ため、足すと電話番号ログインが止まった。

その依存は、送信ボタンを `t-submit` にして明示したことで無くなった。そこで根本原因として
`button.vue` のルートに `type="button"` を足した。呼び出し側が `type` を渡せば属性の引き継ぎで
そちらが勝つ（レンダリングして確認）。form 内の `t-button` はすべて既に `type` を明示しているので、
既存の画面の挙動は変わらない。次に form を作る人が `type` を書き忘れても送信しない。

## 直し方

- サインイン「次へ」: `<t-button @click="onSignin">` → `<t-submit>`。入口を form の `@submit` だけにする
- 各キャンセル: `type="button"` を明示する（`t-button` は `type` を prop として宣言していないので、
  そのままルートの `<button>` に落ちる）

## PhoneLogin も直す

最初は除外していた。invisible reCAPTCHA が `id="signInButton"`、つまり**キャンセルボタン**に
紐づいていて、type を変えると SMS 認証の挙動が変わりうると考えたため。

実機で測ったら除外は要らなかった。`handleSubmit` の先頭が `console.log("submit")` なので、
reCAPTCHA や SMS に頼らず「送信処理が走ったか」をブラウザのログで数えられる（reCAPTCHA は
実際に読み込まれた状態）。

| 操作 | 修正前 | 修正後 |
|---|---|---|
| 送信をクリック | 送信処理1回 | 1回（壊れていない） |
| キャンセルをクリック | **SMS 送信処理が走る** | 走らない |
| 電話番号欄で Enter | **キャンセル扱いで画面を離れる** | 送信処理1回 |

reCAPTCHA はキャンセルのクリックを止めていなかった。キャンセルに `type="button"` を足し
（`id="signInButton"` は残す）、送信ボタンは `t-submit` にして暗黙の submit への依存をなくした。

確認コード入力の form（2段目）は、実際の SMS を受け取らないと到達できないので実測していない。
直し方は1段目と同じ。

## 確認

- **修正前のコードで同じ Playwright スクリプトが落ちること**（4ケース）、修正後に全ケース通ることを確認
- Enter キーでの送信が1回で維持されること
- 同じ種類の不具合を `yarn test` で捕まえるガード（`test/unit/test_formButtons.ts`）。CI に e2e が無いので
  ブラウザ検証は CI で回らない。許す形を列挙し、それ以外を報告する
- ガードはテンプレートを **Vue のコンパイラで**読む。正規表現だと `v-on:click` や束縛された `:type`、
  複数行の要素を読み違える

## 送信中の二重送信（レビューで判明）

Enter が送信に届くようになった結果、**送信中にもう一度 Enter を押すと重ねて送信される**経路が
できた。読み込み中の覆いはマウスしか止めないので、キーボードは素通りしていた。応答を保留した状態で
実測すると、サインイン・再設定・電話番号でいずれも2回送信された（再設定はダブルクリックでも）。

判定は `src/utils/beginSubmit.ts` の純関数にまとめ、各ハンドラの入口で使う（手書きのコピーが
何か所もあると、別の画面のように1つだけ逆になる）。`SignUpPage` の既存の形（送信ボタンを `:isDisabled` で
無効化）に無効化された既定のボタンは Enter による暗黙の送信も止める。

送信中の判定は**失敗したときだけ戻す**。成功時に戻すと、画面の遷移（user の監視や親の確認を待つ）が
起きるまでの間に再送できてしまう。ただし電話番号の SMS 送信は、成功すると確認コードの form に
進むので成功時も戻す。

失敗したあとの再送は、判定そのものは戻るが、**画面によっては既存の仕組みで止まる**。サインインは
再送できる（実測）。再設定と電話番号は、失敗のエラーが送信ボタンを塞ぐ既存の不具合があり、入力を
変えるまで送れない。今回の変更より前からあり、omochikaeri-docs#185 に切り出した。

## サインインの form に novalidate を付ける

`@click` を外して form の submit を通すようにしたことで、`type="email"` のブラウザ標準検証が
サインインの唯一の入口になった。2020 年から 2025 年 12 月まで新規登録はこの検証を通っていない
（`@click` から直接呼んでいた）ので、**ブラウザの文法に合わないアドレスで登録された既存のアカウントが
締め出されうる**。サインインは登録時のアドレスを受け付けなければならないので `novalidate` を付け、
判定を Firebase に任せる（以前と同じ）。

## パスワード未入力のエラーを訳す

Enter が送信に届くようになったので、パスワードを空のままメール欄で Enter を押すと
`auth/missing-password` が返る。翻訳キーが無く、生のキーがメール欄の下に出ていた（main でも
「次へ」を押せば出ていたが、Enter の経路では画面を離れていたので見えなかった）。全言語に訳を足し、
パスワード欄の下に出るようにした。

## 見送り

- 電話番号ログインの reCAPTCHA がキャンセルボタンに紐づいている件 → omochikaeri-docs#184。
  描画先を変えると SMS 認証そのものが止まりうるが、手元で確かめる手段が無い
- 認証まわりの既存の不具合（失敗後に送れない、表示名の保存を待たない等）→ omochikaeri-docs#185
- 読み込み中の覆いがキーボードを止めない件（注文の確定・二段階認証など、アプリ全体）→ omochikaeri-docs#186

## CI で守る

送信中の判定は、画面の処理が Firebase・store・router に依存するので単体では動かせない。そこで
`test/unit/test_beginSubmit.ts` で、関数そのものに加えて**各ハンドラで `beginSubmit` の判定が
Firebase を呼ぶより前にあること**を TypeScript の構文木で確かめる。判定を消しても、Firebase の後ろに
移しても赤になる。

あわせて、form には送信するものが必ず1つあることもガードで見る。`t-button` は送信しないので、
送信ボタンを `t-button` に置き換えると送れない form になる。
