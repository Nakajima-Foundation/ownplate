# 画面側の割引額の規則を Firebase から切り離して試験を足す

SingularitySociety/omochikaeri-docs#212

## 何をしたか

`src/utils/promotion.ts` は先頭で Firebase の auth と firestore を読み込むので、
中の純粋な規則に単体試験が書けなかった。そこに**客の請求額を下げる規則**が入っている。

`src/utils/promotionRules.ts` に切り出したのは5つ。

- `getPromotionCollctionPath` / `getPromotionDocumentPath` — 券の置き場（店舗どうしの境目）
- `userPromotionHistoryPath` — 使用履歴の置き場（客どうしの境目）
- `promotionDiscount` — 使える注文額かと、いくら引くか
- `isPaymentAllowed` — カード決済専用／現地払い専用の縛り

置き場の2つは元から export されていたので、呼び出し元2箇所の import を書き換えた。
再輸出はしていない。composable の外枠（`watchEffect` の位置、`ref` の初期値、
`onUnmounted` の後始末）は触っていない。

残り（管理画面の並び順、使用済みの券を外す絞り込み、履歴を引く鍵の振り分け）は
性質が違うので別に扱う。

## 挙動が同じであることの確かめ方

**読んで確かめてはいない。旧の式をそのまま写して、並べて走らせた。** 二段構えで測った。

### 1. 規則そのもの

店舗 id・券 id・客 uid（空・スラッシュ入り・`..`・全角・`__proto__`）、注文額
（0・境目・負・小数・NaN・Infinity）、しきい値、種別、割引の値、支払い方法の縛りを
総当たり。**違いは出なかった。**

### 2. `watchEffect` の依存の取り方

これは規則の比較では見えない。**旧と新の `watchEffect` を同じ reactive に対して並べて
動かし**、注文額を動かす／券を差し替える／券を外す／関係ない欄だけ動かす、といった
筋書きごとに「割引が使えるか・割引額・**effect が走った回数**」を突き合わせた。
**すべて一致した。**

### 3. どちらの harness も、壊して効きを確かめた

直した行を一つずつ壊すと、規則側は8通りすべてで、依存側は割引計算に関わる3通りで差が出た。
依存側については、**新しい側だけ注文額の依存を1つ落とす**変異も試し、実行回数まで
食い違うことを見た（`2` 対 `1`）。戻すとどちらもゼロに戻る。

足した試験も同じ8通りで壊し、すべて赤くなった。

## 画面とサーバの割引額が一致することを試験にした

同じ規則が `functions/src/functions/order/promotion.ts` の `getDiscountPrice` にも
書かれている。**ずれると客が見た額と請求額が食い違う。** 両方を同じ入力で呼んで
一致を照合する試験を足した。片方だけ丸める変異で赤くなることを確かめてある。

## 確かめていないこと

決済画面を開いて券を選んではいない。開発サーバを立てて、変えた5つが解決して配信されること、
2つの画面の import 先が正しいことまで。
