# Callable Functions の入口の検証に試験を足す

## なぜ

`functions/src/lib/validator.ts` は、外から来た値が Firestore の道筋や Stripe への
問い合わせに渡る前に、形だけを見て弾く層。ここを通った値は奥まで届く。

試験は2件しかなく、どちらも「正しい値が通る」ことだけを見ていた。**弾くべきものが
弾かれているか**は一つも見ていない。

## 足したもの

`functions/tests/unit/validator_test.ts` に追加した（`yarn ci_test` に入っている）。

- **数と文字列の下ごしらえ** — 桁数・大小・長さ・種別の上限下限、全角の数字、前後の空白
- **id の形** — `..`、`/`、`.`、空白、引用符、波括弧、ヌル文字を通さないこと。
  店舗と注文の id はそのまま Firestore の道筋に入るので、ここが一番効く
- **外の仕組み向けの形** — バーと下線を許す版、base64 と url 向けの版の違い
- **呼び出しごとの決まり** — 注文の作成・状態変更・確定・中身の差し替え、Stripe のつなぎ、
  LINE のつなぎ、通知の引き換え、疎通。それぞれについて「通る形」「必須が欠けたとき」
  「形が違うとき」を分けて見ている

返すのは真偽ではなく理由つきの一覧なので、**欠けているのか形が違うのか**まで照合している。
取り違えると、呼び出し側が出す案内が変わる。

## 留めた挙動のうち、読む人が知っておくとよいもの

- **決まりに無い欄は見られない。** 余分な欄を付けて送っても検証は通る
- **空と見なすのは `null` と `undefined` と空文字だけ。** 0 は空ではない
- **見ているのは型と形だけで、値の範囲は見ていない。** 注文の状態に使われない数も通る
- **行の一覧は空でも通る。** 中身が空かどうかは後段の話

## 確かめ方

`cd functions && yarn ci_test` が緑。`yarn lint` と `yarn build` も通る。
実装には触れていない。
